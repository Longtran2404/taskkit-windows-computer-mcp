# Owner Computer Use permissions — review candidate 0.4.2.dev1

The optional **persistent bridge profile** lets the owner choose apps and capabilities once, then use that scope across windows and clean reconnects without repeated consent dialogs. Defaults stay `authorization_mode=legacy`, physical/semantic input disabled, window-only capture. Installing or connecting alone creates no grant. This document describes code for review, not activation on the owner's computer.

## What identity is authenticated

This repository is a local stdio MCP server. It has no verified integration that imports ChatGPT's native Computer Use permission. The [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) separates HTTP authorization from stdio credentials supplied outside protocol messages. [OpenAI's Computer Use API](https://developers.openai.com/api/docs/guides/tools-computer-use) describes an action/screenshot integration; it does not give this bridge a grant to a local Windows machine merely because it is installed.

Each locally enrolled profile has its own random bearer credential and explicit policy. The configured AI host supplies `TASKKIT_CLIENT_ID` and `TASKKIT_CLIENT_SECRET` through its secure launch environment. The bridge verifies that credential against the DPAPI-protected profile before using policy. The secret is removed from the server environment before native children spawn; no MCP tool accepts or returns it. Client `initialize.clientInfo` and `_meta.client_id` are self-reported labels, not account authentication. A different profile, missing/wrong key, replaced initialize object, changed label or different SDK session cannot borrow an existing connection lease.

**Identity here means possession of the enrolled bridge-profile credential under the Windows owner account. It does not authenticate a ChatGPT/OpenAI account or exclusively attest a host binary.** Any process with that credential can act as that profile. Use a distinct credential per host, protected host secret storage, and a separate Windows account/desktop if stronger isolation from same-account code is required. The bridge does not store a plaintext secret, write it into Codex config, create an OAuth integration, open a network listener or install a service.

The constrained MCP APIs cannot enroll, extend or resume grants, and cannot automate the protected owner permission UI. Arbitrary code already running as the owner can call local enrollment/storage code or modify same-account policy; this bridge cannot provide an OS security boundary against such code. Host sandboxing and owner-side setup remain necessary.

## One-time owner setup

1. Run the installed bridge/AI host from the owner's interactive Windows desktop. Call `bridge_health` in the intended MCP connection. Compare process session, window station, thread desktop and input desktop. A sandbox desktop such as a separate `CodexSandboxDesktop` in the same session still differs from `Default`; grant scope does not fix that isolation. No desktop switching or elevation is performed. A missing foreground window also leaves context unverified.
2. Review local `bridge_config.json` eligibility once: explicitly list app executable names. Keep physical mode disabled unless real mouse/keyboard use is wanted. App-only eligibility uses `semantic_control_mode=app_session`. Physical/file-copy eligibility uses `mouse_control_mode=foreground_session`. Broader capture modes must be explicitly enabled first. The panel cannot widen these local eligibility limits. Executable names include all current/future windows of those names, not publisher/path authentication; avoid broad interpreters/terminal hosts unless that scope is intended.
3. Open the owner panel using the installed interpreter: `python -m win10_bridge_mcp --permissions`. The installer offers `-OwnerOnboarding` as an explicit option. Every app/capability checkbox starts unchecked. Select scope and a finite **1, 7 or 30-day** policy lifetime, then check the local owner consent box. Mutation capabilities require explicit `capture_window` selection for fresh tokens; Notepad file copy also requires `uia_read`. The panel explains these dependencies and rejects missing selections rather than silently granting screenshot/text access.
4. Enroll the profile. Its credential is shown locally once, masked initially. Place it in the intended host's secure launch environment; do not paste it into chat, source, command arguments, public config or logs. There is no automatic credential registration with the host and no generic secure-store integration has been verified for every host. If the host cannot safely supply the environment credential, retain legacy mode. Lost credentials require a new explicit enrollment and revocation of the old profile.
5. Explicitly set `authorization_mode=persistent` locally and restart that configured host/bridge connection. This cloud review does not perform these actions. A valid active profile now covers exactly its selected apps/capabilities, so a second window of a selected app does not open another consent dialog. Existing target identity/geometry/DPI/focus/cursor guards and fresh single-use capture tokens remain necessary. Mutation tools still default to dry run. Host-side confirmations for sensitive actions remain independent.

The panel and all bridge consent dialogs are marked as protected authorization surfaces. Window capture, UIA and physical target APIs refuse them and their owned dialogs, even if `python.exe` is allowlisted. A named local mutex excludes desktop/monitor/region capture while a permission surface is open and prevents a new surface appearing during desktop capture. Close the owner panel before testing desktop scopes. No automatic redaction of other applications is implemented.

## Lifetime, pause, revoke and reconnect

Policy is encrypted/authenticated with Windows **current-user DPAPI** and stored under `%USERPROFILE%\Win10_ComputerBridge\permissions`, with protected owner/SYSTEM ACLs. See [DPAPI's account/machine limitations](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata). This protects against other-user reads/tampering; it is not a sandbox against arbitrary code running as the owner. Files contain a credential digest, selected scope, expiration and state, never the raw credential.

Every server run claims a new random connection marker. Only one run can use a profile at a time. The SDK session object, initialize object and its immutable value snapshot are bound when requests begin; repeated initialize with identical fields still cancels the old lease. There is no permission inferred from a matching display name, previous token, OAuth login or new connection alone.

- **Clean idle EOF:** cancel the runtime lease, clear image tickets, and release the on-disk running marker. A new connection must authenticate the credential again; valid unexpired policy applies without a new owner dialog.
- **Cancelled/in-flight request, uncertain mutation cleanup, crash, or active preview at disconnect:** retain a running marker or pause the policy. Reconnect fails closed until the owner inspects results and uses the local panel's recovery/resume. Abandoning an async handler does not prove the sync thread/native child or owned-key cleanup has finished.
- **Esc/F12, closing preview, `close_live_view`, `pause_access`, emergency stop:** permanently stop this process and persistently pause its profile. A failed pause write leaves the prior running marker, so automatic restart cannot bypass stop. Polling/OS race limitations still apply.
- **Owner Pause/Resume:** change revision/state locally; active leases become invalid. Resume requires a new authenticated connection. It does not extend policy expiration or scope. The agent has a reducing `pause_access` tool and no grant/renew/resume tool.
- **Owner Revoke:** terminal for that credential/profile. Re-enrollment is required. A release from an older run cannot overwrite a concurrent revoke.
- **Expiry/config/scope change:** abort/discard at parent guards and native worker checks. A lease cannot outlive its monotonic deadline even if wall time moves backward during that run. After process restart, expiration still relies on the owner's OS clock; this is not a trusted-time service.

UIA actions already dispatched to providers can finish after cancellation, and physical input may have partial effects. Checks and events are not atomic. Native processes remain disposable and bounded; no physical fallback is added. Recover only after checking the application state and any held keys/buttons.

## Evidence and limits

The previously reviewed **aa446eca662e176cff257950b24a93ba193079d9** had green Windows/Ubuntu Python 3.11/3.13 unit/smoke CI. Parent-relayed owner probes on that revision verified one synthetic PrintWindow capture (916×689, DPI 96) and app-only SetValue/Invoke/Select/Scroll. Cursor changed around SetValue while a consent dialog intervened, so its cause is not established; the later three operations kept the cursor snapshot unchanged. Foreground remained the fixture in snapshots. These observations do not verify this new permissions code, real PDF annotation/save, physical input, CAD or GPU compatibility.

Cloud tests for this upgrade use synthetic credentials, fake DPAPI/ACL/COM/Win32 adapters and real MCP SDK cancellation/EOF control flow. Windows DPAPI ABI/ACL enforcement, named-mutex protection, actual owner onboarding, host secret storage integration and desktop health APIs require owner-run manual checks. No persistent access or credential was activated on the user's computer by this cloud task.
